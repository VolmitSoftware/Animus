# Animus Editor

The browser editor for Animus. It is a client-mode Jaspr app on arcane_jaspr, served at `animus.volmitsoftware.com` from Firebase Hosting (project `animus-editor`, also reachable as `animus-editor.web.app`).

The first screen starts a workspace: blank and named, seeded with the example packs from `../examples/packs` (embedded at build time by `tool/embed_starter_packs.dart`), or opened from a data folder (`plugins/Animus`, or `config/animus` on mod servers) as a directory pick or a zip. Workspaces are listed there with Rename, Duplicate, Export zip and Delete (confirmed; Restore brings the last one back until you close the tab). Every document is checked against the schemas in `../schema` in the browser, and the workspace and its undo steps (50) are kept in IndexedDB. Each document has Visual, Preview, Code and Split views. Nothing is uploaded, and no server is needed for any of it.

## Frame, theme and keyboard

The editor runs on arcane_jaspr's shadcn renderers with the Midnight theme, the Animus pink as primary and focus ring, the library's own radius and Geist (`lib/config/animus_stylesheet.dart`; the few patches over the library are in `lib/config/theme_css.dart`). The library's interaction runtime is shipped as `web/arcane-runtime.js` and loaded with `defer`, because the CSP allows scripts from this origin only. Regenerate it after every arcane_jaspr update:

```sh
dart run tool/write_arcane_runtime.dart
```

The frame is a fixed-height grid: the top bar (brand, the server and workspace switcher, Search, Undo and Redo, the Mode switch and one overflow menu), the nav (jobs with counts, then Recent and Changed; an icon rail at 1100 px and below, a drawer at 760 px and below) and the save bar stay on screen, and only the page body scrolls. The save bar is the one place to save or apply: in a browser workspace it says the edit is kept (or why not, with Save again and Export zip), in a server workspace it counts the changes not applied and holds Apply and Review. Mode is Simple or Advanced, kept per browser (`animus.mode`); Advanced adds jobs, the Form, Code and Split views and rare fields, and Simple never drops data it does not show. Simple keeps to its own jobs' documents in Search, Recent and Home's Needs attention too; an Advanced kind's list address offers Switch to Advanced instead. The kit of components every screen uses is in `lib/ui/`.

Shortcuts, outside text boxes (Cmd on a Mac, Ctrl elsewhere): Mod+K or `/` Search (documents first, then commands; recent documents when nothing is typed), Mod+Z undo, Mod+Shift+Z or Mod+Y redo, N New document, B the NPC list and `?` the shortcut sheet, which lists these and every local shortcut. Mod+S works while typing too: Apply on a server, Saved in this browser. The keys live in one registry (`lib/components/shortcuts.dart`, tested by `test/shortcuts_test.dart`). Escape closes Search, the sheet, a menu, a dialog or the drawer. Undo and Redo are stored beside the workspace (50 steps each) and their notices say what they reverted ("Undid: edit Baker"). Each step keeps what its change left: after a server refresh changed the document it takes back only its own change (a three-way merge), and when the server changed the same field it writes nothing and says "Can't undo: Baker changed on the server." The theme is the dark Midnight theme until the light one is picked in the overflow menu.

Saves that the browser refuses (out of space, storage switched off) keep the edit on screen and the save bar names the cause, with Save again and Export zip. Without IndexedDB the editor works in memory and says so above the page. Tabs of one browser stay in step over `BroadcastChannel('animus.workspace')`: an idle tab reloads a workspace another tab saved, and a tab whose workspace was deleted elsewhere goes home. Each open workspace takes the Web Lock `animus.workspace.<id>` (`BrowserWorkspaceLocks` in `lib/services/browser.dart`); `EditorStore.ownedByThisTab` says whether this tab holds it. Closing the tab asks first while an edit waits to be stored or Code text is not applied.

The brand mark is `web/assets/brand/animus-mark.svg` (the Animus triangle, stripe and diamond in the brand pinks and greys). `web/favicon.svg` is the mark on the near-black tile; `favicon.ico` (32 px, PNG inside), `apple-touch-icon.png` (180 px) and `icon-512.png` are rendered from it. `firebase.json` caches `/assets/brand/` for a year as immutable, so a changed mark needs a new file name. Show the mark with `<img src="/assets/brand/animus-mark.svg" width=".." height=".." alt="">`, or `BrandMark(size: ..)` in Dart.

## Dropdowns

Every choice is arcane_jaspr's shadcn combobox (`ArcaneCombobox`), through `AnimusSelect` (`AnimusSelect.values` for a list of strings); `SuggestInput` stays the editor's own for free text with suggestions. `test/no_native_select_test.dart` fails on a native `select` or `datalist`. Past eight options a dropdown has a search field. Keys: arrows, Enter, Escape (focus goes back to the trigger). A dropdown given `references` picks a document and ends with "+ New <kind>" and "Manage <kinds>": New opens the create form with the search text as the name and the current document's folder, and Create comes back with the new document picked (`lib/state/document_return.dart`); Manage opens the kind's list.

`dropdowns_browser.cjs` checks keyboard-only picking, a click pick, the row label naming the trigger and "+ New rig" and Manage, at 1440 and 390 px in both themes.

## Working without a server

New document (`#/workspace/<id>/new`) lists every kind with a guided first step that makes a valid document (`lib/logic/offline/new_documents.dart`): an NPC from its name, folder, body, skin (a PNG file or address, kept as `editor/skins/<hash>.png` so the preview wears it after a reload) and position, with a behavior from a template; behaviors from the greeter, dialogue, patrol, shop, guard and quest templates; packs, routes, shops, chest GUIs, menus, holograms, rigs (empty or a block figure), animations (empty, bob or wave), skins, text animations and presets. Schematics are not editor documents. Every document has Rename, Duplicate and Delete (confirmed, undoable); a move takes along the NPCs that list a renamed behavior and the animations and NPCs of a renamed rig. Diagnostics offer fixes where the editor knows the repair (`lib/logic/offline/document_fixes.dart`).

An NPC's Preview draws the rig its `rig` names, with its animations playable. A behavior's Preview is a dry run (`lib/logic/offline/dry_run.dart`): pick a trigger, step through what the NPC says, asks and walks to, answer prompts (the matching `dialogue_choice` trigger runs next), flip conditions only a server can answer, and see commands, combat, building and shop trades listed as server only, not run. An NPC that lists the behavior speaks on the stage.

Send to server (`#/workspace/<id>/sync`) works once a server is paired: it picks the server (a dropdown when there are several), compares as soon as the server is online and lists the workspace as New, Changed and Same; Apply checks the selection with the server's validators and sends it as one change set, new documents with no base and replaced ones against the revision and hash the compare saw, so a copy that moved in between is not overwritten, and asks before it replaces a document the server holds differently. Advanced adds Pull (the server's documents copied in as one undo step, keeping local edits unless told otherwise), a Send checkbox per document, Validate alone and a change note. The workspace stays local.

## Building

Needs Dart 3.13 or newer. arcane_jaspr is a path dependency at `.deps/arcane_jaspr`:

```sh
cd animus-web
tool/link_arcane_jaspr.sh            # symlink ~/Developer/RemoteGit/ArcaneArts/arcane_jaspr; or pass a path
dart pub get
dart run tool/embed_schemas.dart     # after any change under ../schema
dart run tool/embed_starter_packs.dart  # after any change under ../examples/packs
dart run tool/extract_minecraft_world_assets.dart --jar=<26.3 client jar> --version=26.3
dart run tool/format_css.dart       # after editing web/styles; test/css_scan_test.dart checks the format and counts rules and declarations
dart analyze
dart test
dart run jaspr_cli:jaspr serve       # development server on :8080
dart run jaspr_cli:jaspr build       # static site in build/jaspr
python3 tool/serve_site.py --port 8098
```

CI clones arcane_jaspr into `.deps/arcane_jaspr` at a pinned ref instead of the symlink.

The 3D preview draws with textures and models from the Minecraft client, which are Mojang's and never committed: `web/assets/mc/` is gitignored, and the extraction tool writes `web/assets/mc/26.3/` (block and item atlases, `models.json`, `blockstates.json` for terrain and block states, the entity and painting textures in `mcEntityTextureIds`, about 4 MB) from a client jar before `jaspr build`. It reads only `assets/minecraft/` from the jar and makes no network request. Any 26.3 client jar works, for example the one Loom or NeoForm keeps in `~/.gradle/caches`. Without the pack the editor works and the stage says the pack is missing. Extract it again whenever `mcEntityTextureIds` grows: a pack from before draws the new bodies white, and `test/model_pack_test.dart` fails on it.

Vanilla entity models are code in the client, not assets. The player, armor stand, horse, turtle, frog, llama, armadillo and dragon rigs are written by hand (`lib/mc/rigs/`); every other mob comes from `lib/mc/rigs/mc_vanilla_layers.g.dart`, which `tool/generate_entity_layers.dart` writes by running `tool/entity_layers/DumpEntityLayers.java` against a 26.3 client: it builds the client's own layer definitions and poses each model with its `setupAnim` for an idle entity, and once more per line of `tool/entity_layers/layers.txt` that names a second pose (`CAT@sitting=...;isSitting=true`). `lib/mc/rigs/mc_mob_bodies.dart` says which layers, textures, tints and poses each body type and its settings stack; `lib/mc/npc/npc_objects.dart` draws the painting, item frames, falling block, end crystal, displays and dropped item. Regenerate after a Minecraft update:

```sh
dart run tool/generate_entity_layers.dart --jar=<26.3 client jar> --classpath=<its libraries, joined by :>
```

The browser checks run against a built site you serve yourself. `test/support/shell.cjs` holds the frame helpers (open the nav or its drawer, open a document through Search, switch the Mode, read the save bar, list every document of a workspace). Every script refuses to start without `ANIMUS_WEB_URL` (the served site), and the ones that talk to a server without `ANIMUS_FAKE_URL` (your own fake server); never point them at a shared port. `ANIMUS_SCREENSHOTS` is optional and should point outside the repository. 

Serve the site with `tool/serve_site.py` rather than `python3 -m http.server`: the standard server queues only 5 connections, and under the load of several checks it resets some of the parallel stylesheet requests a page makes. `serve_site.py` answers on threads with a queue of 128 (`--port`, `--bind`, `--directory`, default `build/jaspr`). ## Connecting to a server

`/animus editor pair` on a server prints a link to `#/pair/ANM1....` (the Animus menu's Web editor button runs it). Opening it, or pasting it into Pair a server on the start page, shows one card: the server's name, when the link runs out, what the editor may do, this browser's name and Remember this browser; Advanced adds the fingerprint and paths. Pair exchanges the one-time secret for a token over the first path that answers with that fingerprint, then replaces the address so the secret does not stay in history, and lands on the server's Home. A link that cannot work says why in one sentence with the next step (`pairProblemFor` in `lib/components/server/pair_copy.dart` words each refusal) and, when the link is spent, a field for a new one. The token is kept in sessionStorage, or in localStorage too when "Remember this browser" is on; saved servers are listed once each under Continue on the start page with their state from one `hello` each.

Each paired server has one connection (`lib/services/server/server_connection.dart`). It tries the direct path (`<directUrl>/animus/v1`, fetch and a WebSocket whose first frame is `event-auth`) and the relay (`<relayUrl>/app`, subscribed by fingerprint) in turn, the last good one first. Every `hello` must carry the pinned fingerprint, or the path is refused and nothing more is sent. When a path drops, the other is tried at once; after that it retries every 1, 2, 4 up to 30 seconds, and "Retry now" skips the wait. While online over the relay with a direct path paired, it probes the direct path (15, 30, then every 60 seconds, and at once when the browser comes back online or the tab becomes visible); once `hello` answers with the pinned fingerprint and a direct event stream has stayed open beside the relay stream for 2 seconds, new requests go direct, requests already sent finish over the relay, and events seen on both streams are delivered once. A failed probe leaves the relay session alone. A refused, expired or revoked token asks for a new pairing. Mutating requests carry `X-Animus-Counter`.

## Live editing

A paired server opens as a server workspace (`#/server/<id>`), next to the local ones. The whole catalog (every page, each entry with a summary: name, type, place, features) is its library, so lists show every document with its name at once; the documents themselves are read in the background with batch reads (`POST /v1/documents/read`, 200 per call, 4 at a time, retried after a `rate-limited` hint) and join the workspace with the revision and hash they came from. A document opened before it arrives is read first. Each document is one IndexedDB record, so a keystroke writes one record whatever the workspace holds. The save bar at the bottom says what waits (changes not applied, a read in progress as "Loading n of m", documents that could not load with Retry, a restart, "Open in another tab" with Take over) and holds Apply; its Review opens a sheet (`lib/components/server/live_bar.dart`) with the changed documents (what changed in a few words, Discard), the ones with problems (Fix), the ones changed on the server too and Apply:

- Apply: validates first, then every change (edited, new or deleted) as one change set with its base revision and hash. A document changed on the server since is listed with Compare, Take server and Keep mine and nothing is sent until it is decided. Compare is the three-way merge (base, mine, server): fields only one side changed merge by themselves (Keep both); one field both changed is Take server or Keep mine, and several get a Mine or Server switch each (Use combined). Either moves the change onto the server's revision for the next apply. A newer server change drops the copy Compare read, so Take server always takes the newest. A refusal for a permission the pairing lacks names it and the pair command that adds it to the token's own scopes, with no Retry.
- Validate (Advanced): the server's validators on the changes (or the open document), with their diagnostics shown in the document and the code view, marked as from the server.
- Preview in game (Advanced): the changes and the open NPC shown to the token's player only; End preview stops it. The server refuses commands, combat, economy and trades in previews.
- Undo (Advanced, per apply in the Applied list; also the save bar's Undo right after an apply): the server's rollback receipt for that change set.

Live editing for one server runs in one tab of a browser at a time (a Web Lock named for the server); another tab on the same server waits, says so in its save bar with Take over, and takes over when the first closes. A change set is only sent once its pending record is stored with the workspace. Every refused request and dropped path is shown through one table of causes and next actions (`lib/services/server/error_copy.dart`), which a test checks against every error and relay code in `editor-v1.schema.json`.

Unanswered change sets are kept with the workspace. After a reconnect (or a reload) the editor asks the server what became of each by its idempotency key, and reports one that never arrived; one the server is still writing settles from its `change` event. An event stream the server closed because the editor fell 256 events behind (reason `limit`) is explained, reconnected and followed by a fresh catalog load. Catalog events (sent for every write, whatever made it) refresh documents that were not edited here, one batch read per event; edited ones are marked changed on server at once and listed in Review with Compare, and deleted ones go. Events for documents in a change set still in flight wait for its answer and are checked then, so a write made meanwhile shows at once; a successful apply retires a change set held after a failed answer for the same documents. Over the relay, a change set, check or preview larger than one frame (1 MiB) is refused before it is sent. While the server restarts the relay stays subscribed and the editor reconnects as soon as it is back, retrying every 1 to 5 s for the first minute. The start page checks each saved server with one `GET /v1/hello` (Online, Checking, Not reachable) without connecting, and only the tab that owns a server workspace holds a connection. The server's own schemas (with its modules) drive the inspectors while connected.

## Fake server

`dart run tool/fake_server.dart` starts an in-memory editor-v1 server for local development and tests. It loads `../schema/fixtures/export` (`--data=`) once and never writes to disk. One loopback port (`--port=`, default 9797) serves the direct API at `http://127.0.0.1:9797/animus/v1/`, the browser side of the relay at `ws://127.0.0.1:9797/app`, and test controls at `http://127.0.0.1:9797/__fake/`. Allowed origins come from `--origin=` (repeatable, default `http://127.0.0.1:8098`), and previews show to the `--viewer=` UUID. At start it prints a `Pair:` link with both paths in it. The controls have no auth and answer only loopback callers: `POST /__fake/pair?paths=both|direct|relay` mints a fresh code, `POST /__fake/edit` changes a document on the server side, `POST /__fake/drop {"path":"direct|relay|all","seconds":N}` and `POST /__fake/offline {"seconds":N}` cut a connection or take the server off the relay, `POST /__fake/revoke`, `/restore` and `/reset` do what their names say, and `GET /__fake/state` and `GET /__fake/document?kind=&id=` show tokens, previews, changes, documents and the active test controls. For failure paths: `POST /__fake/pair?days=N` mints a code whose token lives N days; `POST /__fake/expire` expires every token now (body `{"tokenId":"<id>"}` for one, `{"inDays":N}` to move the expiry instead), closing their streams with `token-expired`; `POST /__fake/fail?code=<error-code>&times=N[&route=/v1/...][&scope=<scope>]` answers the next N requests (on that route) with the error (`scope` names the missing scope of a `scope-missing`, as the server's own refusals do); `POST /__fake/drop-answer` writes the next change set but loses its answer and its change event, so the editor must ask `GET /v1/changes/{key}`; `POST /__fake/relay-error?code=<relay code>` sends that relay `error` frame and closes every relay connection; `POST /__fake/limit` closes every event stream with reason `limit`; `POST /__fake/player?online=false` refuses previews with `player-offline` until `online=true`. `POST /__fake/plugins?running=modelengine,mythicmobs,libsdisguises` makes the capabilities answer report those integration plugins running (none by default), so the editor offers their modules and fields. `POST /__fake/live {"npc":"town/walker","world":"world","x":N,"y":N,"z":N}` puts a spawned NPC there for `GET /v1/terrain/position` and the terrain radius; leave out `x` to clear it. It speaks the server's newer protocol additions: catalog `summary`, the batch read `POST /v1/documents/read`, `serverName` in hello and the pair answer, every scope but `apply:commands` by default (`?scopes=` with `read` in it is the exact grant), token expiry that slides on use, and the server's rate limit per token (`--rate=N` per second, default 20, bursts to twice that) with `retryAfterMillis`; `GET /__fake/state` counts the refusals (`rateLimited`, `rateLimitedTotal`). `POST /__fake/offline` now takes the direct path down too, as a restart does. `POST /__fake/edit` takes `"origin": "server"|"file"` for the event's `source`; `POST /__fake/delete {"kind","id"}` deletes on the server side; `POST /__fake/touch {"kind"?,"count"?}` rewrites documents as a reload does and sends the coalesced catalog frames. It answers as the Java server does in these too: spawn and despawn write `spawned` and raise the revision with an `editor` catalog event; at most 8 requests run at once per token (the ninth gets `429` with `retryAfterMillis` 250); at most 10 pair attempts a minute per address; an id that does not fit its kind is `invalid-request`; and every `429` and `503` carries `retryAfterMillis` and `Retry-After`. `POST /__fake/fail` takes `retryAfterMillis=` (default 50 for `rate-limited`, 500 for `busy`), `POST /__fake/slow?ms=N` holds every request N ms in its slot (0 turns it off), and `POST /__fake/pair?folders=town,town/market` mints a token limited to those NPC folders (`group-denied` elsewhere). `--scale=N` builds N generated documents (about 500 NPCs, skins, behaviors and shops at 1200) instead of `--data`, and `--name=` sets the server name.

## Inspectors and code view

NPC definitions and behaviors have structured Visual views built from the generated schemas and `completions.json`, or from the connected server's schemas, which include loaded modules. The NPC inspector is described under NPC browser and editors; fields it does not lay out render generically, with help from the schema descriptions. The behavior editor reads top to bottom: the document (with the server switch), typed variables, routines as a collapsible tree, then triggers. Every node type of the behavior language is editable: sequence, action, condition, wait, repeat, foreach, while, break, continue, parallel, call, return and set. A collapsed row shows the node's type and a plain line ("Say: Welcome", "While count < 3"); Up and Down move between rows, Right and Left open and close one, Delete asks before removing it. Wherever the language takes an operand (`set.value`, `repeat.count`, `foreach.list`, `return.value`, call arguments) one control picks a value typed by the target, a declared variable of a compatible type, an expression, or a template with `{{ }}` holes. Expressions and templates are monospace fields that check the Gloss grammar with the behavior roots, facts and functions as you type and complete names below the field. An action or condition argument can be a null placeholder filled at run time from a variable, an expression or a template; the editor writes the null and the pointer in `bindings`, `expressions` or `templates`. Conditions test a capability or an expression. List, map and any variables have typed starting values. With the server switch on, NPC-only events, scopes and capabilities are hidden and timers start at 20 ticks. Keys the editors do not know are kept. `server-behaviors.json` has its own Visual view: add server behaviors from the workspace, remove and reorder them. In the Code view, Ctrl+Space (or typing in a string) completes keys and values from the same schemas, and names inside expression and template strings. The gutter marks lines with diagnostics, and a list under the text jumps to each one; server diagnostics are tagged. Text that is not JSON gets one message with its line and column, and the line is marked.

Simple shows Order, Loop and Speed; More settings holds Travel (`mode`), Style, Wait, Random picks (`seed`), Start at (`startOffset`), Spread (`jitter`), Link reach (`linkDistance`) and the wander size. Waits are typed in seconds and stored in ticks (`lib/logic/npc/route_fields.dart`); a wait is one number or, with Range, a shortest and a longest (`[min, max]`). A picked point shows its position and wait, and its More holds its own spread, style, speed, teleport, `weight` (random only) and Next points (`next`, sequence only). `lib/logic/npc/route_model.dart` checks every field as the server's `WaypointSettings` does; a problem shows at its field, the rest are listed under the map in words ("Point 4, next point 2") with a link that picks the point, as terrain problems are. Every edit writes one key, so keys Simple does not show keep their values. The map redraws only when what it shows changes.

## Trait groups and recordings

A group (`groups/<id>.json`) opens in the same tabs over its `values`, with Members in place of Basics: its description, its members as a list that opens each one (Remove from group for the picked ones) and Add members, which picks more from every other NPC in one undo step. Look carries the skin and the skin pool; Movement, Talk and trade, Combat, Attributes and Modules are the NPC's, without a position. The values are checked as NPC fields the way the server's `GroupDocument` does (a probe definition, errors under `$.values`). An NPC's Basics (Advanced) lists its groups in merge order, with add, remove, move earlier and a warning for a group the workspace lacks, and under What it takes the merged definition (`lib/logic/npc/group_model.dart` over `group_merge.dart`, the shared merge that `schema/fixtures/groups/cases/` pins): one row per field and per module with the group or NPC that set it, a link to that group, and the whole effective JSON. The stage draws the effective definition. In Advanced the NPC list's Trait group action adds the picked NPCs to a group or takes them out, as the server's `groups assign` does (filter the list by folder or tag and press Ctrl+A to reach a folder or a tag): one commit, so one Undo step and, on a server workspace, one change set at the next apply. An unknown group, or one that would give an NPC more than 16, writes nothing.

Recordings (`recordings/<id>.json`, made in game with `/animus record`) open as a preview (a top-down drawing of the recorded steps with event marks) with one playback row under it (Play, the scrub, the time in seconds) and the preview speed in its header, the details beside it (description, tags as one comma list, default playback Once, Loop or Back and forth, speed, Make route), Events under the preview, and the jargon facts (frames, frame gap, start point, pose changes, recorder, size, version) in Advanced (`lib/logic/recording/recording_facts.dart`). Start here and End here on the scrub mark a range and Trim cuts the frames outside it as one undo step. Frames are otherwise not edited. Code applies a draft only when it passes the server's recording rules. The page header renames a recording, which updates the NPCs and route steps that play it. Movement (`#/workspace/<id>/list/route` and `/list/recording`; `#/workspace/<id>/recordings` shows the Recordings tab) lists routes and recordings on two tabs from `store.library`: every route with the NPCs that use it, every NPC with points of its own as "Name's route" (read from the NPC documents, since the catalog summary says "route" for both kinds; NPCs not read yet are counted), and every recording with its length, world and players.

## Rig editor

A rig's Visual view (and an animation's, which opens its rig) is the rig editor (`lib/components/rig/`). When the editor is at least 64rem (1024 px) wide the bone tree, the stage and the inspector sit side by side with the timeline under them; narrower (a smaller window, or the form column of Split) the stage stays on top and Bones, Inspector and Timeline tabs show one pane (a rig opens on Bones, an animation on Timeline). A toolbar above holds Rig only or With body (and the preview body), Import .bbmodel and Download server files.

- Bone tree (`rig_tree.dart`): add a child, rename in the name field (saved on leaving it or with Enter; tracks in the rig's animations follow), reparent (with its subtree, rest pose unchanged because pivots are rig space), delete from the "..." menu after a confirmation that counts the tracks it takes along (children move to the parent). It is a `role=tree` with `aria-level` and the tree keyboard model (Up, Down, Home, End, Right to the first child, Left to the parent; selection follows focus). The 64-bone, depth-16 and parents-first rules of `schema/rig-v1.schema.json` are kept.
- Inspector (`rig_inspector.dart`): pivot, rest rotation, visual type (item, block or text display, or none), item id, count and `components`, item context, block state, text, billboard, background, line width and shadow, visual offset, rotation and scale, and sockets. `body` (hidden, or shown on one of the eight preview bodies) is in the toolbar.
- Stage (`RigStage` in `rig_gizmo.dart`, in the kit's stage frame with Move, Rotate and Scale in its header and one status line under it): the bones drawn as the client draws the display entities (item displays turned 180 degrees and centred, block displays from their corner, text displays), a sample item at each socket, the skeleton, and move, rotate and scale handles. In the rest pose a handle edits the pivot (with the subtree), rest rotation or visual scale; with an animation open it keys the bone at the playhead on the selected track, changing that track's own value (`lib/logic/rig_gizmo_edit.dart`). Handles are focusable and nudge with the arrow keys; `placeHandles` (`lib/logic/rig_view.dart`) keeps them inside the canvas and apart, larger on touch screens.
- Timeline (`rig_timeline.dart`, `rig_keyframe_panel.dart`, `rig_events.dart`): an empty state until an animation is picked, the animation picker (labelled with the rig's names) and New animation (a dialog for its name), the clip's loop and length (seconds beside the ticks) and playback (speed, play), a ruler with tick numbers, a lane per track with draggable, focusable keyframe diamonds (visible tracks shade their hidden spans), and the events lane. A selected track has its blend, order and delete; a selected keyframe its tick, value, easing (`linear`, `hold`, `ease_in`, `ease_out`, `ease_in_out`, `back_out`, `bezier(...)` checked against the schema pattern at the field), copy to the playhead and delete; a selected event its tick, capability (`animus:play-sound` or `animus:spawn-particle`) and the arguments from `completions.json`. Add keyframe keys the selected track, or the first one for the channel, or a new replace track; New track always adds one, and the key bar's "..." menu adds an add or multiply track. Deleting a track, keyframe or event from its "..." menu asks first. A shorter length asks before trimming what falls past the end. Playback uses `lib/logic/rig_sampler.dart`, the Dart port that matches the shared goldens; a `once` clip hands over to the rig's `idle` when it ends, as `RigPlayback` does.
- Animation names (`rig_animations_panel.dart`, a section under the timeline that starts open while a name needs a fix): the rig's `animations` map, with `idle` and `walk` marked as the names navigation plays, rename in place, repoint, open and remove. A name whose animation is missing or animates another rig is marked (and is a `rig-animation-missing` or `rig-animation-rig` warning from `validateRigAnimations`), with Create for a missing one.
- Import .bbmodel: every group becomes a bone, its cubes an item model at `pack/assets/animus/models/item/<rig path>/<bone>.json` with an item definition and the embedded textures beside it, and every Blockbench animation an animation document. The import is bounded (16 MiB file, 4,096 elements, 16 textures of at most 1024 px width, 64 animations, 256 keyframes per channel) and refuses a file over a bound. Cube rotations in 22.5-degree steps stay on the element; others become their own bone. Sound keyframes naming a vanilla sound become `animus:play-sound` events, and a keyframe with two data points becomes two keyframes a thousandth of a tick apart. Molang values, catmullrom and bezier curves, particle and timeline keyframes and non-cube elements are approximated or left out, each counted in the import summary.
- Download server files: downloads `<rig>-server-files.zip` with the rig, its animations and the `pack/assets/` sources its bones use, laid out as data-folder files; `/animus pack build` on the server turns them into the resource pack. The pack layout and zip format are in [wiki animus/04-npc-definitions](https://github.com/VolmitSoftware/docs/blob/master/animus/04-npc-definitions.md#resource-pack-layout), and `schema/fixtures/pack/` (written by `dart run tool/write_pack_fixture.dart`, checked by `test/pack_fixture_test.dart`) is what the server's importer must match. Export zip (top bar) downloads the whole workspace the same way.

Every edit is a workspace commit to IndexedDB and can be undone; gizmo drags commit once on release. Files under `pack/assets/` are kept as workspace resources when a folder or zip is opened.

## GUI editors

Chest GUIs, shops, holographic menus and holograms (Gloss formats, wiki animus/11-guis-holograms-menus and wiki animus/10-shops) have visual editors, adapted from Gloss Web's editors. Visual shows the editor beside its live preview, Preview the preview alone, and Split the editor beside the code.

- Chest GUI: the window painted like the client's (title in the Minecraft font, item icons meshed by the stage renderer at their `gui` pose, counts, name and lore tooltips; a slot's accessible name carries its name and lore, and Preview shows them on tap). Click a slot, or Tab to it and press Enter, to edit what draws it: a mask key, an explicit slot or the list template. A brush paints keys into the mask by pressing and dragging. Tabs edit the window (title, size, mask rows, `show`, close on teleport, refresh mode and ticks, `select`), keys, the list (area, variable, source, page size, template), variants (which fields each replaces; the window shows and edits the chosen one) and named action lists. Icons take count, count format, custom model, head refresh, name and lore.
- Shop: pages (reorderable) and modes (in switch order), the buy, sell and trade grids painted as the shop window with its bottom-row controls, the owner and up to eight containers, and per entry its type, item, display, price, trade goods, command entries (with the allow-list note), limits with resets, stock, discount, permission and broadcast. Changing an entry's type removes the fields the new type refuses. A shop with containers offers only trade and static entries, without price or stock, as `ShopDocument` requires. Lowering a page's rows warns about entries left outside it. Preview has page and mode tabs.
- Hologram: typed rows (text, item with count, name and lore, head, block, entity), each with `show` and `scale`, reorderable; pages with `show`; variants with their own style; the anchor, yaw and pitch, the eighteen display style fields in collapsed groups, refresh, click box and actions, drawn in the 3D stage. Heads draw without a skin and entities as a labelled box.
- Menu: components with offset, `show`, motion, hover feedback, click box and tooltip, icon styles, list flow, slider and tab styles, tabs with separate ids and labels, menu constants (`vars`) and renamable named action lists, drawn in front of the viewer in the 3D stage. Clicking a component on the stage selects it.
- Text animation: frames (add, remove, reorder, edit), mode, interval and `show` beside a preview that cycles the frames as core picks them, with pause and frame stepping; it starts paused under reduced motion.
- Presets: the presets document's per-kind defaults and named presets (`extends`, values). A chest GUI, hologram or text animation that names a preset is refused by core; its editor offers to copy the preset's fields in.
- Actions: only the actions in `schema/gloss/source.json` that the surface accepts are offered, with fields per type (give and take items with count, name, lore and custom model; `inventory` args as JSON with the parse error at the field; a sequence step's "At tick"). Changing a type keeps the nested lists the new type has and asks before dropping others. A refused action, component, icon or field is flagged with its exact path, as the server words it.
- Expressions: text and condition fields check `{{ }}` holes and expressions with the engine copied from Gloss Web (`lib/logic/gui/gui_expr.dart`), complete names and functions as you type, and previews fill holes with a sample viewer.
- New and Rename create and move GUI documents; Import and Export Gloss bundle read and write `gloss-editor-workspace` files (chest GUIs, menus, holograms, text animations, presets; documents with `animus:` actions are skipped on export). Ids map as the server's `gui import gloss` and `gui export gloss` map them: a Gloss id comes in as `gloss:<id>`, and an Animus id goes out as its path in namespace `gloss`, otherwise as `<namespace>.<path>`. An export also writes the Animus id as the Gloss title, and an import takes it back when it maps to the Gloss id, so an exported bundle imports to the same ids. Folders, titles that are not ids and images are listed on import as not kept; `glossConflicts` lists imported ids the workspace already has.

Browser checks beyond the schemas are in `lib/logic/gui/gui_validation.dart`. The Java parsers are authoritative.

## Deploying

The editor is live at https://animus.volmitsoftware.com. To deploy a new build from this folder:

```sh
dart run tool/extract_minecraft_world_assets.dart --jar=<26.3 client jar> --version=26.3
dart run jaspr_cli:jaspr build
GOOGLE_APPLICATION_CREDENTIALS=<service account path> npx -y firebase-tools deploy --only hosting --project animus-editor --non-interactive
```

Never paste, print or commit the service account key. `firebase.json` sets the cache rules, the single rewrite to `/index.html` and the security headers; scripts load only from the site, so the app runs without arcane_jaspr's inline fallback scripts. The relay deploys separately to Cloud Run; see [relay/README.md](relay/README.md#cloud-run).
