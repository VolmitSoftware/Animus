# Editor contracts

The files under `schema/` are the contracts between the plugin, the relay and `animus-web`. Java tests in `core` and Dart tests in `animus-web` read the same files, so a change that one side does not follow fails a build. The design behind them is in [editor-design.md](editor-design.md).

## The schema folder

| Path | What it is | Source |
| --- | --- | --- |
| `generated/npc.schema.json`, `behavior.schema.json`, `pack.schema.json`, `completions.json` | NPC, behavior and pack schemas plus editor completions for the built-in capabilities | Generated by `BehaviorSchemaGenerator` through the converter's `schema` command |
| `shop-v1.schema.json` | Shops (`shops/<namespace>/<path>.json`) | Hand-written to match `ShopDocument` |
| `gui-inventory-v1.schema.json` | Chest GUIs (`gui/inventories/<namespace>/<name>.json`), the Gloss inventory format as Animus reads it | Hand-written to match `GuiDocument` and `GuiParser` |
| `rig-v1.schema.json`, `animation-v1.schema.json` | Rigs and animations | Hand-written; the format in editor-design.md section 4 |
| `server-behaviors-v1.schema.json` | The server behaviors list, `server-behaviors.json` at the data folder root: `{"schemaVersion":1,"behaviors":["ns:id"]}`, at most 256 distinct ids, no other keys | Hand-written to match `ServerBehaviorList` |
| `editor-v1.schema.json` | Every `/animus/v1` request, response, change set, diagnostic, event and relay frame, one `$defs` entry each | Hand-written |
| `editor-v1.endpoints.json` | Methods and paths with their scope and message definitions, error statuses, document kinds with folders and apply scopes, pairing defaults and limits | Hand-written |
| `gloss/` | Gloss schemas copied unchanged for the adopted kinds, and `source.json` with the Gloss commit and the supported, Animus-only and refused GUI actions | Copied from Gloss |
| `fixtures/` | Golden documents, messages, pairing codes, rigs, clips, sampled transforms and an example data folder; `fixtures/index.json` lists each with its expected result | Hand-written |

Regenerate the generated schemas after changing capabilities, the behavior language or NPC validation:

```sh
./gradlew syncEditorSchemas
```

`SharedSchemaContractTest` fails while `schema/generated/` differs from the generator. After any change under `schema/`, run `dart run tool/embed_schemas.dart` in `animus-web/` so the editor embeds the new copy; its test fails until then.

## What each side checks

Java (`core`):

- the generated schemas match the generator;
- every document fixture with `expect.java` is accepted or refused by `NpcDefinition`, `BehaviorCompiler` (after the catalog's revision check), `PackManifest`, `ShopDocument`, `GuiDocument` and `ServerBehaviorList` as listed;
- `EditorScope` and `DocumentKind` match the scope and kind enums and the endpoint table;
- `PairingCode` decodes and re-encodes every valid pairing fixture byte for byte and refuses every invalid one;
- `EditorIdentity` reproduces the relay handshake golden, and `EditorRelayClient` answers the `relay-request` fixtures with the `relay-response` and `relay-event` fixtures;
- `gloss/source.json` action lists equal the GUI parser's tables;
- `fixtures/gui/ids.json`: chest GUI, holographic menu, hologram and text-animation paths map to `namespace:path` ids and back, relative `|animation.<id>|` references resolve in the referencing document's namespace, and Gloss ids map as `GlossIds` does;
- `fixtures/gui/text-animation-frames.json`: `TextAnimation.frame` picks every listed frame.

Dart (`animus-web`):

- every shared schema compiles with the validator, which refuses any keyword it does not implement;
- every document fixture validates against its kind's schema as `expect.schema` says, and every message fixture against its definition;
- every endpoint names existing definitions and scopes;
- the export fixture opens into exactly the documents in `fixtures/export.expected.json`;
- the Dart sampler matches every golden sample;
- the editor locates, resolves and maps the ids in `fixtures/gui/ids.json`, moves workspaces saved with the old plain-path hologram, text-animation and menu ids as its `migration` list says, and picks the frames in `fixtures/gui/text-animation-frames.json`.

The schemas check structure. The Java parsers stay authoritative: `fixtures/documents/shop/id-mismatch.json` passes the schema and is refused by Java, which the index records. The editor adds the location checks (ids against paths) itself.

## Pairing codes

A pairing code is `ANM1.` followed by the payload JSON (`pairing-payload` in `editor-v1.schema.json`) in base64url without padding. Fields are written in the order `v`, `directUrl`, `relayUrl`, `fingerprint`, `serverKey`, `tokenId`, `secret`, `expiresAt`, `label`, `serverName`, without whitespace, so a decoded code encodes to the same text. A code needs `directUrl`, `relayUrl` or both. `directUrl` is `https://`, or `http://` only on `127.0.0.1` or `localhost`. `relayUrl` is `wss://`, or `ws://` only on `127.0.0.1` or `localhost` for a relay run locally. `fingerprint` is `sha256:` and the hex SHA-256 of the raw 32-byte Ed25519 key in `serverKey`. The link is `https://animus-editor.web.app/#/pair/<code>`. `core/.../editor/PairingCode.java` implements this.

## Relay frames

The relay's frames are the `relay-*` definitions in `editor-v1.schema.json`; `relay` in `editor-v1.endpoints.json` lists which side sends which. `fixtures/editor/relay-handshake.json` is a registration golden: an Ed25519 seed, a nonce and the signature over `animus-relay/1 ` followed by the nonce. Ed25519 signatures are deterministic, so `EditorIdentityTest` (Java) and the relay's `server_identity_test.dart` both reproduce it byte for byte. The relay's `relay_frame_test.dart` decodes every `relay-*` message fixture on the side that sends it. The protocol is described in `animus-web/relay/README.md`.

## Rig sampling

The browser and the server sample animations the same way. `fixtures/animation/samples/` pins the result within 0.0001 for translations, scales and matrix entries and 0.01 degrees for rotations.

1. **Playback time.** A layer plays a clip at `speed`; at `t` ticks after it started, clip time comes from `t * speed` and the clip's duration `D`:
   - `once` and `hold`: `min(max(t, 0), D)`. They differ only in what happens after the end: `once` ends the layer, `hold` keeps the last pose.
   - `loop`: `t - D * floor(t / D)`.
   - `pingpong`: `p = t - 2D * floor(t / 2D)`, then `p` if `p <= D`, else `2D - p`.
2. **Track value.** Keyframe ticks strictly increase. At or before the first keyframe the value is the first keyframe's value; at or after the last, the last one's. Between keyframes `a` and `b`, `u = (time - a.tick) / (b.tick - a.tick)` and the value is `a + (b - a) * ease(u)` per component, using `a`'s easing (default `linear`). `visible` tracks step: the value is `a`'s.
3. **Easings,** with `u` clamped to 0..1: `linear` u; `hold` 0; `ease_in` u^3; `ease_out` 1 - (1 - u)^3; `ease_in_out` 4u^3 below 0.5, else 1 - (-2u + 2)^3 / 2; `back_out` 1 + 2.70158 s^3 + 1.70158 s^2 with s = u - 1; `bezier(x1,y1,x2,y2)` the CSS cubic Bezier from (0,0) to (1,1): solve x(s) = u for s, return y(s). These are Gloss's clip easings.
4. **Channels.** Every bone starts each sample with rotation (0,0,0), translation (0,0,0), scale (1,1,1) and visible true. Layers apply in order, and within a clip tracks apply in document order: `replace` sets the channel, `add` adds per component, `multiply` multiplies per component. `visible` always replaces. Animation channels are relative to the rest pose.
5. **Bone transform.** With `R(e) = Rz(e.z) * Ry(e.y) * Rx(e.x)` (Euler degrees, X applied first, right-handed, column vectors), a bone's local transform is `T(pivot - parentPivot) * T(translation) * R(restRotation) * R(rotation) * S(scale)`, with parent pivot (0,0,0) for bones without a parent. Its model transform is the parent's model transform times the local one; bones without a parent start from `Ry(-yaw)`, the body yaw in Minecraft degrees (0 faces +Z, 90 faces -X). A bone is visible when it and every ancestor are visible.
6. **Visual transform.** A visual's display transform is `model * T(visual.translation) * R(visual.rotation) * S(visual.scale)`. Display entities take it as translation, left rotation, scale and right rotation; any decomposition that reproduces the matrix is correct, so the fixtures pin the matrix (12 numbers, rows of `[r0 r1 r2 t]`).

The server's segment planning (2-tick samples merged while linear within 0.01 blocks and 0.5 degrees) is built on this sampler and is not part of the shared contract.

## Transport notes

- The direct listener serves the API at `/animus/v1/`. A browser's WebSocket cannot carry headers, so on the direct path the first frame of `/v1/events` is `event-auth`, sent within 10 seconds; the listener passes its token to the handler as the `Authorization` header, which is what the relay forwards. A refused stream closes with code 4000 plus the HTTP status and the error code as the reason.
- `POST /v1/imports` takes the file's raw bytes on the direct path. Over the relay, whose frames carry JSON, the body is a JSON string holding the bytes in base64; the listener hands the handler the same form. A relay frame is 1 MiB, so files larger than about 756 KiB need the direct path; the editor says so before it sends anything.
- The import endpoints run the drop-in flow (`CitizensDropIn`) through `EditorImports`: uploads land in `imports/saves.yml`, `imports/shopkeepers/save.yml`, `imports/shopkeepers/config.yml` and `imports/dtltraders/`, and every answer is an `import-review`. Each step is audited, and apply, accept and rollback send one catalog event for the documents they changed. Tokens limited to NPC groups are refused.
- Change ids are the journal transaction ids, so `POST /v1/changes/{changeId}/undo` replays the rollback receipt. Idempotency records live in `state/editor/changes/<key>.json` and are written in the same transaction as the documents.
- On apply the server sets `revision` to the stored revision plus one for npc, behavior, shop, inventory, hologram, presets, rig and animation documents.
- The `server-behaviors` kind is one document, id `server-behaviors`, at `server-behaviors.json` in the data folder root (its folder in the endpoint table is empty). It carries no `revision`: `ServerBehaviorList.parse` refuses any key but `schemaVersion` and `behaviors`, so it is not revisioned and reports revision 0. It applies with `apply:behaviors`; an apply, undo, import or hotload of it reloads the behavior catalog, which re-reads the list. Ids are checked as behavior ids; whether each names a behavior with `"server": true` is a warning in the editor and a refusal to run on the server.
- `completions.json` publishes the expression language under `language.expressions` (roots, reserved names, facts per root, flag scopes, behavior and standard functions, the readable-name pattern and the length limit), each capability's `reach` (`npc` for capabilities that need an NPC body, otherwise `both`), and each server event's `context` keys. `behavior.schema.json` has one root rule on `server`: with it, only server events, a timer of at least 20 ticks and execution, player or global scopes; without it, only NPC events.
